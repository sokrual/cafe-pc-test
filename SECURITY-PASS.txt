Repository: sokrual/cafe-pc-test

Base: main at 163f4d7df8e7005d68a3e150919720e20896811c (merge of PR #9)
Scope: final read-only review. No application code changed.

SUMMARY

The core server, watchdog, lock screen, and installers have useful security controls. They are not yet safe to expose to real customers without addressing the High findings below.

Most important findings:
- HIGH: Level A is still watch-only. A Customer can run programs the owner has not approved. The gaming PC installer also does not set firmware/USB boot protections.
- HIGH: the counter installer does not enable or verify BitLocker. A stolen counter PC or disk can expose the database and its DPAPI machine keys if the attacker can get offline access.
- HIGH: each offline PC can accept the same person's same authenticator step while disconnected. The server rejects the duplicate later, but both PCs have already granted play time.
- HIGH: a profile reset restores the original Customer registry hive and can erase the most recently remembered time-lock setting. An offline PC can then fail to lock at zero after a customer changeover.
- HIGH: offline authenticator secrets are copied to every PC. A PC administrator/SYSTEM compromise exposes every owner's and staff member's offline secret, not just one person's.
- HIGH: a lost phone's offline authenticator cannot be revoked on PCs that remain disconnected. Those PCs keep the old secret until they next refresh.
- HIGH: the PC token is a clear-text file. Its folder ACL protects it from the normal Customer account, but the secret is not encrypted at rest.
- HIGH: there is no counter database backup and restore process.
- HIGH: the customer app-control policy is not enforcing an allow-list; it is deliberately in audit/watch-only mode.
- MEDIUM: offline logout actions are queued in Agent memory and are lost if Agent or Windows stops before reconnection.
- MEDIUM: offline sale state is replaced atomically but is not explicitly flushed to stable storage before success is returned. A sudden power loss can lose the latest sale or replay marker.
- MEDIUM: shop-network protection is not full network segmentation. Gaming PCs can make other outbound connections; the DNS rules do not stop arbitrary apps using DNS-over-HTTPS or direct IPs.
- MEDIUM: no certificate or PC-token rotation procedure is present.
- HIGH: B4 privacy and legal controls are not built. CHECKS.txt says these privacy checks apply in full; this report does not start B4.

FINDINGS OUTSIDE CHECKS.txt

F1 - HIGH - Customer can run unapproved software
Evidence: install/install-pc.ps1:276-277 deliberately enables Level A in Audit mode; ci/lockdown.ps1:249 checks B3.E5 as watch-only. The user asked us to assess programs brought by customers. This is not an enforced kiosk/allow-list. An unapproved program can read Customer data, make network connections, attack other devices, or exploit a local vulnerability. The current policy is a trial observation mode, not a security boundary.
Also not found: USB storage/device control, firmware setup password, Secure Boot/boot-order enforcement, or a test that an ordinary customer cannot boot another operating system. Treat physical USB/boot access as unprotected until the owner locks firmware and tests it.

F2 - HIGH - Counter PC disk encryption is not enabled by the installer
Evidence: install/install-admin.ps1:39-73 installs the service, ACLs the data folder and sets idle lock, but does not enable/check BitLocker. CHECKS.txt Part 1 explicitly includes BitLocker on the counter PC. If the counter PC or its disk is stolen, disk access may expose the encrypted database's DPAPI-wrapped key and certificate material unless Windows device encryption is separately enabled and recovery keys are safely held.

F3 - HIGH - Offline unlock can grant time twice before reconciliation
Evidence: OfflineUnlockStore.cs:133-155 checks and stores UsedSteps only in that PC's local cache. Cafe.cs:501-502 enforces one person/step in the central database, but that check runs only after reconnect. Two disconnected PCs can therefore both accept the same valid code and grant play time; one sale is later refused and sent to review. AccountTests.cs:Offline_sales_ignore_counter_login_order_and_are_unique_per_person_and_step_across_PCs tests reverse-order reconciliation while the server is available, not simultaneous acceptance while both PCs are offline.

F4 - HIGH - Profile reset can erase the remembered offline time-lock setting
Evidence: Agent/Program.cs:41-58 stores LockWhenTimeRunsOut in HKCU; Agent/Program.cs:123-126 refreshes it from the server. The full logout reset restores the saved clean profile and NTUSER.DAT (Wipe.cs:197-218, 264-273). That snapshot is made during install setup (install/install-pc.ps1:255-270), before later owner setting changes. After a reset, an offline PC can reload the old value rather than the last server answer. Existing UI test Offline_time_limit_locks_only_when_the_last_owner_setting_is_on tests outage expiry, but not after a full customer profile reset.

F5 - HIGH - A single compromised gaming PC can expose every offline authenticator
Evidence: Accounts.cs:110-122 returns all owner/staff offline secrets to every PC. PcProxy.cs:164-166 refreshes that full list into each PC's machine-protected cache. B3.C4c proves the normal Customer user cannot read the cache, but DPAPI LocalMachine is not a defence against local Administrator/SYSTEM or a disk attacker. One PC compromise can therefore expose all staff offline unlock accounts, not only the staff member who uses that PC.

F6 - HIGH - Lost offline-authenticator phone cannot be revoked on an offline PC
Evidence: offline secrets are refreshed only when a PC can reach the server (PcProxy.cs:159-169; periodic refresh at 140-149). A PC that stays offline keeps the old secret. Replacing the secret at the counter cannot revoke it on that disconnected PC until it reconnects. There is no per-PC expiry or emergency disable mechanism for an offline cache.

F7 - HIGH - PC authentication token is stored as clear text
Evidence: install/install-pc.ps1:118-123 copies pc.token into keys as a normal file; PcProxy.cs:105-108 reads it directly. The keys folder ACL blocks Customer (B3.C4b), but a local administrator or someone with offline disk access can read it. Encrypt it with machine DPAPI or LSA and provide a rotation/revocation procedure.

F8 - HIGH - No tested backup and recovery for the counter database
Evidence: STATUS.txt lists B5.5 (daily encrypted backup and restore test) as not started. The server stores the authoritative users, sessions, money ledger, audit and offline sales in cafe.db (Cafe.cs:84-116). A counter PC disk failure or destructive compromise can lose the money records and account data.

F9 - HIGH - Lost-phone response is incomplete
Evidence: counter two-step has a one-use recovery code (Accounts.cs:66-78, 125-134), but the offline-unlock secret is separate (Accounts.cs:81-108) and has no recovery/revocation path for PCs that are disconnected. A lost phone can still produce valid offline codes until every PC refreshes. This overlaps F6 but also requires a documented owner response: revoke/replace both factors, revoke active staff tokens, and check the review list.

F10 - MEDIUM - Offline logout queue is not durable
Evidence: Agent/Program.cs:223-229 stores queued logout only in an in-memory List. The source comment says it is lost if the program is killed while offline. A power cut or process crash before reconnect loses the logout event; the wipe request remains and the PC stays blocked, but the server session is not automatically ended until staff acts.

F11 - MEDIUM - Gaming PC outbound network access is broader than the filter description
Evidence: install/install-pc.ps1:160-190 blocks DNS and DoT to other destinations and turns off browser DoH policies, but it does not restrict general outbound connections. Arbitrary programs can use HTTPS DoH or direct IPs. The server's shop-network allow-list includes broad private/link-local ranges (Cafe.cs:11-25), while the installer firewall uses LocalSubnet (install/install-admin.ps1:75-82). This is not a substitute for VLAN/network segmentation and an explicit allow-list.

F12 - MEDIUM - Offline sale file writes are not explicitly made durable before success
Evidence: OfflineUnlockStore.cs:56-64 writes a temporary file and renames it, but does not call Flush(true) or otherwise request a durable disk flush. The sale and UsedSteps are kept together, which is good, but an abrupt power loss can still lose the most recent acknowledged write or leave a damaged cache. No power-cut test exists.

F13 - MEDIUM - No certificate or PC-token rotation procedure
Evidence: server/Program.cs:174-187 creates a ten-year certificate; PcProxy.cs:105-122 pins it. PC tokens can be revoked by removing the PC (Accounts.cs:27-34), but there is no routine rotation, overlap window or documented renewal test.

F14 - MEDIUM - Local pipe process identity check is path-based
Evidence: PcProxy.cs:327-342 checks the connecting process image path equals Cafe.Agent.exe, after granting pipe access to the Customer SID (PcProxy.cs:203-216). This blocks a different executable, as B3.E4b tests, but does not prove the process has not been injected into or tampered with. No same-user process-injection test was found.

F15 - MEDIUM - Full reset recovery has no real power-cut test
Evidence: Wipe.cs:124-155 and 255-273 contain recovery for interrupted directory swaps and the cleanup lockdown tests cover failed reset/retry (B3.F1d). No test cuts power at each swap/hive stage. The design is defensive, but the required all-moments power-loss claim is not proven.

F16 - LOW - Review queue has no documented retention/owner alert target
Evidence: rejected offline sales are added to audit (Cafe.cs:564-566) and exposed by /staff/review (server/Program.cs:133), but there is no alert, age target or documented process for clearing and resolving them.

F17 - LOW - Counter login tokens have no idle expiry
